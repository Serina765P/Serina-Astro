# Music player and NetEase data-source options

**Research date / sources accessed:** 2026-10-30. This evaluates UI/playback libraries separately from music metadata and stream providers. An MIT player license does not grant rights to third-party music, artwork, lyrics, or private API responses, and recent commits do not establish stream reliability or service authorization.

## Bottom line

- **Maintained UI exists:** Video.js 10 and Media Chrome are actively releasing; native `<audio>` plus local controls is also viable. APlayer has playlist/lyrics features but its published UI is old and cannot be called actively maintained. MetingJS is maintained as a small adapter, but still delegates its UI to APlayer.
- **A reliable, authorized, static-site-only NetEase data feed was not established.** The official NetEase outchain iframe is the only first-party embed found. Meting and the public MetingJS endpoint are unofficial dependencies with no uptime, track-availability, or rights guarantee. The original NeteaseCloudMusicApi is archived for copyright protection.
- Consequently, custom-styled direct-audio playback and automatic NetEase playlist extraction are separate risks. A working HTTP response today is not evidence that all 75 tracks will play in every visitor's browser or remain playable later.

## NetEase metadata and streaming sources

### 1. Official NetEase outchain player (first-party iframe, not a data API)

The [target playlist page](https://music.163.com/playlist?id=8562312822) currently identifies the playlist as **“博客” with 75 tracks** and exposes “生成外链播放器”. The first-party URL `https://music.163.com/outchain/player?type=0&id=8562312822&auto=0&height=430` returned player markup and controls on the research date ([outchain source](https://music.163.com/outchain/player?type=0&id=8562312822&auto=0&height=430)). `auto=0` matches manual start in the URL, but browser behavior still needs verification.

- **Static-site fit:** no proxy, API key, or metadata scraper is needed; NetEase owns playlist loading and media selection inside the frame.
- **Customization:** the parent can style layout around the iframe, not safely reach in and restyle NetEase DOM. Cross-origin window access is limited by the same-origin policy ([MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy#cross-origin_script_api_access)).
- **Limits:** no documented versioned public JSON API or supported parent-side playlist/control contract was found. This is an embed option, not a reliable metadata/stream source for APlayer or custom controls. Track entitlement, regional behavior, frame headers, mobile layout, and future URL stability remain runtime checks.

### 2. Meting (`@meting/core`) — maintained unofficial server/build-time library

Upstream is active: **1.6.2 was published 2026-10-10**, the corresponding npm release workflow succeeded, and the package has npm provenance; MIT ([repository](https://github.com/metowolf/Meting), [release run](https://github.com/metowolf/Meting/actions/runs/38059722275), [npm package metadata](https://registry.npmjs.org/@meting/core/latest), [LICENSE](https://github.com/metowolf/Meting/blob/master/LICENSE)). It documents NetEase `playlist`, `url`, `lyric`, and `pic` operations ([README](https://github.com/metowolf/Meting#music-information)).

- **Where it can run:** the source imports Node `crypto`, uses `Buffer`, and sends provider-specific headers/cookies; it is not a drop-in browser data client ([NetEase provider](https://github.com/metowolf/Meting/blob/master/src/providers/netease.js), [core HTTP code](https://github.com/metowolf/Meting/blob/master/src/meting.js)). With no proxy/server, its only plausible integration boundary is a trusted build machine generating a snapshot—not live visitor playback resolution.
- **Snapshot limitations:** a build can freeze metadata, but direct media URLs can change or lose authorization, and new visitor location/account entitlements are not represented by the build result. Rebuilding refreshes data only when a build is actually run. No durable URL lifetime was found in upstream docs.
- **Documentation caveat:** README says Node.js `>=12`, while implementation relies on global `fetch`; do not infer Node 12 compatibility from that requirement statement ([README](https://github.com/metowolf/Meting#requirements), [implementation](https://github.com/metowolf/Meting/blob/master/src/meting.js)).
- **Reliability/legal:** upstream itself warns that platform APIs can change, availability can be geographic, rate limits apply, and platform terms/copyright must be respected ([important notes](https://github.com/metowolf/Meting#important-notes)). Its NetEase provider reproduces private EAPI request signing and mobile-client headers, so an MIT library license is not evidence of NetEase authorization ([provider source](https://github.com/metowolf/Meting/blob/master/src/providers/netease.js)).

### 3. MetingJS default hosted endpoint — browser-only but third-party

MetingJS defaults to `https://api.i-meto.com/meting/api`, with optional per-element/global replacement ([source](https://github.com/metowolf/MetingJS/blob/master/src/Meting.js), [API precedence](https://github.com/metowolf/MetingJS#api-priority)). On 2026-10-30, an unauthenticated HTTP request for playlist `8562312822` returned JSON containing track names plus URL/artwork/lyric endpoints ([observed response](https://api.i-meto.com/meting/api?server=netease&type=playlist&id=8562312822)).

That one response demonstrates a possible static-client integration, **not** a service-level guarantee. The endpoint is neither NetEase nor the visitor's origin; its availability, CORS policy, response schema, rate limits, logging, and continued authorization are external risks. Audio/artwork requests add further origins. A public endpoint also cannot safely hold a private NetEase cookie or secret. Use of a custom endpoint does not remove the upstream rights/reliability issue.

### 4. Binaryify/NeteaseCloudMusicApi — do not treat as maintained

The original repository is **archived**, and its sole README says “保护版权,此仓库不再维护” (“to protect copyright, this repository is no longer maintained”) ([repository metadata](https://api.github.com/repos/Binaryify/NeteaseCloudMusicApi), [README.MD](https://github.com/Binaryify/NeteaseCloudMusicApi/blob/master/README.MD)). Old npm artifacts, mirrors, or forks do not reverse that upstream status or establish a lawful/reliable hosted API.

### 5. Public playlist HTML — insufficient as a robust stream source

The official playlist HTML exposes useful display metadata and currently reports 75 songs, but it is a web page rather than a documented CORS/JSON feed ([playlist page](https://music.163.com/playlist?id=8562312822)). Browser `fetch()` of cross-origin reads requires CORS; ordinary cross-origin media embedding is a different browser path ([MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy#cross-origin-network-access)). Scraping the page at build time would still leave playback URLs unresolved and add markup fragility.

## Browser, static-site, privacy, and security constraints

- **Manual start is the robust browser path.** Browsers commonly block audible playback without prior interaction; `play()` returns a promise that can reject with `NotAllowedError` ([MDN autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay#the-play-method)). A click-to-start UI also provides a clear point to initialize third-party requests. The manual-start decision does not imply that subsequent track advancement always needs another click; that is a device/browser test.
- **Plain media embedding and JavaScript reading differ.** MDN lists `<audio>`/`<video>` among generally embeddable cross-origin resources, while cross-origin reads normally require CORS ([same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy#cross-origin-network-access)). Thus direct `<audio src>` can be simpler than fetching/decoding audio, but hotlink denial, redirects, unsupported codecs, HTTP range behavior, and mixed content still need actual track tests. Do not add `crossorigin` unless CORS-enabled media processing is needed.
- **Howler/Web Audio is not a CORS workaround.** Howler's default Web Audio mode loads through XHR; its docs recommend `html5: true` for large/streaming files ([Howler options](https://github.com/goldfire/howler.js#html5-boolean-false)).
- **No seamless-navigation guarantee.** A fixed/global player on an Astro static site does not by itself preserve an `<audio>` element across full document navigations. Test whether the intended “global BGM” means a control on every page or uninterrupted playback; uninterrupted playback needs a navigation/lifecycle design that preserves the media element, not merely repeated page markup.
- **Fail closed to silence, not another provider.** MetingJS source has no visible `fetch` rejection handler in its loading chain ([source](https://github.com/metowolf/MetingJS/blob/master/src/Meting.js)). Any custom UI should distinguish metadata failure, individual track failure, and autoplay rejection rather than displaying a playing state when no sound started.
- **Third-party trust boundary:** hosted APIs/iframes receive visitor network requests and can change responses independently of the blog build. NetEase's terms describe automatic server recording of IP, browser, time, and related access information ([service terms, privacy section](https://music.163.com/html/web2/service.html)). Self-host pinned UI assets where practical; do not inject account cookies into public markup or trust an unofficial API as a source of secrets. This is a deployment/privacy consideration, not a claim of a discovered vulnerability.
- **Terms are a separate review item.** NetEase's published terms restrict unauthorized third-party compatible software/plugins and unauthorized copying/use of service content ([§8 and §10](https://music.163.com/html/web2/service.html)). Whether a particular unofficial API integration is permitted cannot be inferred from its open-source license; the first-party outchain player has a different risk profile because NetEase supplies the embed itself. This note is technical research, not a legal clearance.

## Required runtime checks before implementation

1. Load the official outchain iframe from the real HTTPS blog origin in current Chrome, Firefox, Safari, and mobile browsers; confirm it is frameable, starts only on user action, lists/plays target tracks, and handles unavailable/VIP/region-limited tracks.
2. If evaluating MetingJS, verify the hosted endpoint's **actual browser CORS**, complete 75-track response, first/middle/last track playback, redirects, seeking/range requests, lyric/artwork loads, rate limiting, and behavior when the endpoint is offline. Do not substitute the successful server-side HTTP probe above for this test.
3. If evaluating a build-time Meting snapshot, test freshly generated media URLs in anonymous browsers from intended visitor regions and again after an elapsed interval; measure whether URLs expire. Confirm that failure of one song does not stall the whole playlist.
4. Verify keyboard operation, visible focus, accessible names, volume/mute, error announcements, and screen-reader behavior for any custom playlist; neither native playback nor a player library alone verifies the site-specific UI.
5. Test Astro production navigation for the intended meaning of global BGM, plus browser back/forward, page hide/show, and article players starting while BGM is active.
6. Review the current NetEase terms and content permissions for the selected route. Do not promise full-catalog playback, permanent stream URLs, API stability, or legal authorization from any of these libraries.
